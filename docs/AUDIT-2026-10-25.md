# Shopify theme and storefront audit — 25 October 2026

## Assessment

This is a substantial native Online Store 2.0 theme with a functioning purchase path. It is ready for further store acceptance testing, but is **not yet certified for launch across the full device, catalog, editor and app matrix**. The largest remaining concerns are sizing credibility and merchant data, performance measurement, and untested store configurations. A framework rewrite or visual redesign is not justified.

The current working tree contains 66 TypeScript files, 36 authored stylesheets, 58 Liquid sections, 51 snippets, 13 templates, two layouts and two reusable theme blocks. See [the source inventory](AUDIT-INVENTORY-2026-10-25.md) for every source path and section schema inventory. Generated assets were rebuilt and checked rather than treated as a second authored implementation.

This is a repository-wide static assessment with deeper review and tests of commerce, requests, section replacement, navigation, motion and build integration, plus a selected real-store browser journey. An inventory entry or passing lint check does not mean every file's possible configurations were exercised. Historical documentation and prior browser claims are context, not new verification.

Documentation consulted includes README, architecture and product audits, customization roadmap/audit/reference and editor QA, size-chart setup, section sources, previous codebase/storefront reports, update history, product/motion plans, and the original implementation and reference-component matrix. Older planning decisions are sometimes superseded. For example, GSAP is now an approved dependency, sticky buying is now opt-in, and cart recommendations already exist. The previously recorded owner removal of localization selectors, installments and gift-card recipient fields is preserved.

## Essential repairs made in this audit

These changes are incremental and preserve saved layouts, settings IDs and the established visual direction. Pre-existing working-tree commerce, cart, sticky-bar, 404 and styling changes are preserved and are not attributed to this audit.

| Repair | Problem and resolution | Verification |
| --- | --- | --- |
| Respect card media settings | `product-card.liquid` forced alternate media whenever purchase actions existed, bypassing Off / image-only / global secondary-image choices. Removed that override; videos now require eligible automatic hover media, otherwise the configured image/off behavior applies. | Source branch review and Theme Check. Full live editor toggle matrix pending. |
| Validate the entire purchase form | The form deliberately uses `novalidate`; the AJAX handler checked quantity only. A required customization field supplied by an app or custom Liquid could be omitted. It now calls `form.reportValidity()` after picker resolution and before serialization. | New regression proves a blank required monogram blocks add, then a valid value is sent as a line property. |
| Name variant groups accessibly | `<legend>` was inside a header `<div>` instead of being the fieldset's first child. Retained the visual header and connected the group to an explicit label ID with `aria-labelledby`. | Live accessibility snapshot now exposes `group "Size: M"`; layout unchanged. Quick-add ID rewriting already covers ARIA ID references. |
| Escape customer/catalog text | Contact retry/prefill values and textarea content, translated search no-results text, metadata/title values, and navigation/cart labels had missing escaping. Added escaping at the HTML output boundary. | Source review and Theme Check; a harmless markup-like search query created no injected probe elements. No exploit or email submission was performed. |
| Recover from invalid saved fit profiles | Persisted enum values were trusted; an invalid `sex` value makes `BOUNDS[sex]` undefined and can break the fit component. Reject invalid preference enums and nonpositive measurements so the component uses its defaults. | Nine new persisted-profile regressions cover invalid choices/dimensions and valid partial profiles. |
| Patch test dependency | `happy-dom` 20.14.6 was in the affected range of GHSA-834v-8h66-3h79. Updated the exact version and lockfile to 21.0.4. This is development/test code, not customer-shipped JavaScript. | Registry audit now reports zero known vulnerabilities; full tests pass. Video fixture uses an empty `srcdoc` so it tests deferred insertion without remote iframe loading. |

Dependency finding verified against the [maintainer's security advisory](https://github.com/capricorn86/happy-dom/security/advisories/GHSA-834v-8h66-3h79). A clean registry audit is a point-in-time dependency result, not a security certification of all storefront code.

## Customer journey verified this pass

Used the authenticated Shopify development theme at local port 9393, including a 375×812 phone viewport and the initial 831×880 viewport. Additional product-page DOM/layout checks at 320, 768 and 1440px found one main h1, all four size inputs and no horizontal page overflow. This was real Liquid and Shopify commerce, not a static Vite preview.

1. Collection rendered 24 cards from a 34-product catalog, real size controls, sorting and pagination. No horizontal page overflow at the observed widths.
2. On mobile, opened Filter, entered a minimum price of 1000 and applied. Drawer closed, the URL acquired `filter.v.price.gte=1000`, the active price chip appeared and busy state cleared.
3. Opened Amaya. Buying was disabled until a size choice; XL was sold out. Selected M, observed Updating, then the resolved purchase control. The group is now named for accessibility.
4. Added M through the actual theme form. Drawer showed M ×1 and Tk 1,900.00. Increased quantity; drawer and subtotal became M ×2 and Tk 3,800.00, with no visible error.
5. Submitted the drawer's Checkout button. Shopify checkout showed Amaya M ×2, ৳3,800 subtotal, ৳80 shipping, ৳3,880 total, and the store's cash-on-delivery option. Stopped before entering customer data or submitting the order.
6. Returned to the full cart and removed the audit's line. The initially empty test cart was restored to the empty-cart state.

## Essential attention before release

1. **Populate and verify real size charts.** The infrastructure is already comprehensive. Complete [the documented Admin assignments](SIZE-CHART-ADMIN.md) using approved measurements for each fit/category, then compare the inline panel, full guide and quick-add. Do not fill missing measurements with sample numbers.
2. **Make a decision on fit-finder credibility.** `fit-finder.ts` estimates chest from height/weight using fixed coefficients and letter-size bounds; it does not use the assigned garment chart. It can map an estimate to the nearest size the product sells. That can look more authoritative than the evidence warrants, especially across differing cuts. My recommendation is to disable it until calibrated, or rebuild its decision logic against validated category/product data. Changing this existing shopping feature needs your decision; it was not silently removed. Saved-profile validation is repaired independently.
3. **Finish catalog and discovery setup.** The current mobile filters exposed Availability and Price, not a useful size/type/color discovery system. Configure Search & Discovery and accurate product data. Resolve duplicate-looking categories such as Bottoms/bottoms and repetitive product names with explicit color labels where appropriate. This is merchant data work, not a replacement filtering backend.
4. **Run native Theme Editor acceptance.** Use a temporary template or duplicate theme for two differently configured instances, save/reopen, add/duplicate/reorder/remove, hidden tab selection, mobile preview and app blocks. Source contracts are a useful gate but cannot prove setting persistence or every CSS cascade. See [the existing matrix](EDITOR_CUSTOMIZATION_QA.md).
5. **Test the remaining commerce fixtures.** Real multi-option/color products, changing inventory, high variant count, quantity limits, subscriptions/apps, distinct line properties, discounts, gift cards, external video/3D and additional currencies if planned. `product-form.ts` handles string properties and a selling-plan ID; it does not provide a subscription selector itself and does not serialize uploaded File properties. App/file customization must be integrated and tested before selling such products. These are conditional requirements, not reasons to add every app to this apparel store.
6. **Complete device/accessibility checks.** Real iOS Safari and midrange Android, on-screen keyboard/safe areas, touch dragging, keyboard-only use, VoiceOver/TalkBack, text zoom and reduced motion. Viewport emulation alone is not a phone performance test.
7. **Measure performance on representative content.** Run repeatable Lighthouse/trace tests against the built unpublished theme, then inspect real-user metrics after launch. No current LCP, INP, CLS or Lighthouse score is claimed here. Budget/animation decisions below require measurement, not assumptions based on bundle size alone.
8. **Verify store operations.** Test contact/newsletter delivery, approved policies, shipping zones/rates, COD procedure, tax setup, enabled payment methods and an authorized test order/refund workflow. Those are Admin/operational settings, not theme-side implementations. No messages, subscribers, catalog edits, policy changes or real orders were created by this audit.

## Performance and animation assessment

Current production-build output, gzip sizes rounded from Vite (decimal KB):

| Asset | Gzip | Implication |
| --- | ---: | --- |
| Global JS entry | 8.26 KB | The shared entry itself is modest; static and lazy imports also count. |
| Product JS entry | 7.37 KB | Product-specific enhancement, plus its imported graph. |
| Global CSS | 28.35 KB | Much component CSS is imported globally despite lazy JavaScript. |
| Product CSS | 4.64 KB | Roughly 33 KB combined with global CSS before additional component styles. |
| GSAP + ScrollTrigger + SplitText chunk | 47.68 KB | One shared chunk; simple reveals can cause all of it to load. Lazy import does not mean absent from initial page work. |
| OGL/flex-carousel chunk | 25.64 KB | Additional optional graphics cost; preserve the native fallback and existing lightweight phone mode. |

These are individual asset sizes, not measured total network transfer or Core Web Vitals. The manifest includes shared dependencies, and page content/settings determine dynamic loading. Do not add independent gzip sizes and label the result an observed page load.

The architecture has good safeguards: no SPA router, native scrolling, scoped cleanup, safe static fallbacks, background/offscreen pause, capped DPR for the graphics carousel and reduced-motion handling. Keep those. Performance opportunities, requiring approval where architecture changes:

- Separate ordinary reveals from the full GSAP/SplitText load or gate plugins more narrowly. Expected benefit: lower parse/transfer work on ordinary shopping pages; **not** a guaranteed 47.68 KB saving while any other component still requests that chunk.
- Reduce eager HTML/media in inactive collection tabs. Panels are currently server-rendered and enhanced to hide; lazy images do not remove their HTML/DOM cost. A fetch-on-first-use design must retain no-JS content, keyboard behavior and editor selection. Request timings and Liquid render cost need profiling.
- Audit the global CSS imports by page/section. Split only where measured savings exceed extra request/maintenance cost. Tailwind correctly omits preflight and maps tokens; there is no need for a new styling framework. Existing shared and Riviera rules are a cascade maintenance concern, not an automatic reason to rewrite them.
- Use smaller mobile hero video sources/posters and retain explicit pause controls. Media compression/source choice will often matter more than adding another entrance animation. The current card setting repair also lets merchants actually turn alternate media off.
- Protect the purchase path from decorative delays. Keep option feedback immediate and allow the existing queued submit during variant resolution. Prefer a measured, bounded cache of authoritative section responses over an untested browser-side price/stock engine.

These recommendations follow [Shopify's theme performance guidance](https://shopify.dev/docs/storefronts/themes/best-practices/performance), which emphasizes reducing main-thread work, appropriate media priority and measuring actual scripts/content.
